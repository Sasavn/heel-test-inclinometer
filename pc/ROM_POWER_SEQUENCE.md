# ESP32-P4 rev 301/302: питание flash при ROM-восстановлении

Источник алгоритма — официальный Espressif esptool, функция `power_on_flash`
в [зафиксированной версии esp32p4.py](https://github.com/espressif/esptool/blob/93477aceb5bc28971db26223a60339bb53e9390a/esptool/targets/esp32p4.py#L263).
Адреса LP/PMU дополнительно сверены с `hw_ver3/soc/{reg_base,lp_system_reg,pmu_reg}.h`
из ESP-IDF 5.5.2. Перенесён регистровый протокол в собственный C++ ROM-движок;
Python-код esptool в программу не включён и при работе exe не исполняется.

Локально установленный esptool 4.12.0 тоже содержит последовательность ECO6/ECO7,
но для ECO7 с `DOWNLOAD_MODE_XPD_ON` обнуляет весь PMU_DATE. В указанном новом
официальном варианте исправлено сохранение остальных битов DATE; использован
именно этот вариант, а не полное обнуление регистра.

## Перед любым изменением регистров

Проверяются локальные четыре части, SHA/MD5, разметка без NVS, ROM SYNC без stub,
chip ID 18, отсутствие secure boot/download и шифрования, eFuse-read ревизии,
диапазоны обоих настоящих образов. Ошибка завершает сеанс до power sequence,
SPI attach, стирания и записи flash. Если используется USB Serial/JTAG, затем
отключаются watchdogs по прежней отдельной последовательности Espressif.

## Обычный путь ECO6/ECO7

Только для ревизии 301 или 302. `RMW` означает отдельное чтение, затем запись
полного значения с изменением указанных битов. Все ответы ROM проверяются.

| Шаг | Операция |
|---|---|
| 1 | WRITE `0x5011010c` = 1 (pad group) |
| 2 | ожидание не менее 10000 мкс |
| 3 | RMW `0x501151bc` OR `1<<27` (current limit) |
| 4 | RMW `0x501151b8` OR `1<<7` (force tie-high) |
| 5 | RMW `0x501153fc` OR 3 |
| 6 | ожидание не менее 50 мкс |
| 7 | RMW `0x501151bc` AND NOT `1<<27` |
| 8 | RMW `0x501151b8` AND NOT `0xff<<23` |
| 9 | RMW `0x501151b8` OR `0x80` |
| 10 | RMW `0x501151b8` AND NOT `1<<7` |
| 11 | ожидание не менее 1800 мкс |

Напряжение не выбирается произвольно: используется существующая конфигурация
платы в eFuse через PMU. **Записей в eFuse нет**. Задержки реализованы
`sleep_for(microseconds)`; реальная ОС может ждать дольше, но не должна сокращать
минимальное время. ROM-модель подменяет ожидания и проверяет их точное место.

## ECO7, питание уже включено ROM

Для 302 сначала читается `0x5012d034`. При установленном бите 16
(`DOWNLOAD_MODE_XPD_ON`) обычная последовательность не выполняется. Читается
`0x501153fc`; только если оба младших бита равны 1, они очищаются через RMW.
Остальные биты сохраняются. Если оба бита уже не установлены, запись не нужна.
На этом пути нет трёх задержек и нет записей pad/current-limit/target.

Только после успешного завершения нужного пути идут SPI_ATTACH/SPI_SET_PARAMS,
запись приложения, проверка MD5, загрузчик, таблица и otadata последней.
При отказе чтения, записи, задержки или отмене до attach не отправляются erase,
DATA или END. Сеанс не продолжает работу с предположительно включённой flash;
нужен новый запуск полного восстановления.

## Границы проверки

Тесты ROM-модели проверяют порядок команд, исходные ненулевые значения регистров,
сохранение чужих битов, ветви ECO7, ошибки/таймаут/отмену и MD5 всех четырёх частей.
Дополнительно используются неизменённые настоящие файлы `build-rev3/package`
на виртуальных 301/302. Это проверка программной реализации протокола, а не
аппаратная проверка напряжения, драйвера USB, задержек ОС или конкретного Tab5.
